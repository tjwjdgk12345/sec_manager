# 취약점 시나리오 정리 (XSS / SQLi / IDOR)

> 1주차 산출물. 각 취약점에 대해 **발생 시나리오 · 사전 조건 · 탐지 신호 · 성공 판정 근거**를 정리한다.
> 이 문서는 이후 Detector/Verifier 구현 시 "무엇을 근거로 취약/성공이라 판단하는가"의 기준표 역할을 한다.
> 대상 예시는 OWASP Juice Shop 기준(제공 예정)이며, 그 전에는 범용 테스트 사이트로 대체한다.

공통 원칙: **허용된 테스트 사이트에만** 자동 요청/브라우저 조작을 수행한다. 페이로드는 파괴적이지 않은(non-destructive) 최소 형태를 사용한다.

---

## 1. XSS (Cross-Site Scripting)

사용자 입력이 이스케이프 없이 페이지에 반영되어 공격자가 주입한 스크립트가 피해자 브라우저에서 실행되는 취약점.

### 1.1 유형별 시나리오

| 유형 | 발생 위치 | 사전 조건 | 대표 흐름 |
|------|-----------|-----------|-----------|
| 반사형(Reflected) | 입력값이 같은 응답에 즉시 반영 | 입력 파라미터가 응답 본문/속성에 그대로 출력 | 검색창/쿼리 파라미터에 페이로드 → 응답에 실행 가능한 형태로 반영 |
| 저장형(Stored) | 서버에 저장 후 다른 페이지에서 출력 | 입력이 DB 등에 저장되고 후속 조회 시 렌더링 | 리뷰/댓글/프로필에 페이로드 저장 → 조회 페이지에서 실행 |
| DOM 기반(DOM-based) | 클라이언트 JS가 입력을 DOM에 삽입 | `innerHTML`, `document.write`, `location.hash` 등 사용 | URL fragment/파라미터를 JS가 위험한 sink로 전달 |

### 1.2 사전 조건
- 값이 반영되는 입력 지점(파라미터, 폼 필드, 헤더, URL fragment) 식별
- 출력 컨텍스트(HTML 본문 / 속성값 / JS 문자열 / URL) 파악 — 컨텍스트별로 필요한 이스케이프가 다름

### 1.3 탐지 신호
- 입력한 마커 문자열(`<b>`, `"`, `'`, `<`, `>`)이 **이스케이프 없이** 응답/DOM에 등장
- 주입한 요소가 실제 DOM 노드로 파싱됨 (텍스트가 아니라 태그로 인식)
- 스크립트 실행 콜백(예: 고유 값을 남기는 non-alert 페이로드) 발동

### 1.4 성공 판정 근거
- **DOM 증거**: 주입 페이로드가 태그/속성으로 파싱된 DOM 스냅샷
- **실행 증거**: 주입 스크립트가 실제로 실행되었음을 보여주는 부작용
  - PoC에서는 `alert` 대신 `window.__xss_marker` 전역 변수 설정, `title` 변경, 고유 DOM 노드 삽입 등 **검증 가능한 부작용**으로 확인
- 요청/응답 쌍 + 화면 변화 스크린샷 기록

### 1.5 PoC 안전 페이로드 예시
```
"><img src=x onerror="window.__xss_marker='HIT'">
<svg onload="document.title='XSS_'+Date.now()">
```
> `alert()`는 브라우저 다이얼로그로 자동화가 멈추므로 검증에는 부작용 기반 마커를 쓴다.

## 2. SQLi (SQL Injection)

사용자 입력이 SQL 쿼리에 문자열로 결합되어, 입력으로 쿼리 구조 자체를 바꿀 수 있는 취약점.

### 2.1 유형별 시나리오

| 유형 | 신호 채널 | 사전 조건 | 대표 흐름 |
|------|-----------|-----------|-----------|
| 오류 기반(Error-based) | DB 오류 메시지 | 오류가 응답에 노출됨 | `'` 삽입 시 SQL 구문 오류 메시지 반환 |
| 불리언 기반(Boolean-blind) | 응답 본문의 참/거짓 차이 | 오류는 안 뜨지만 결과가 조건에 따라 달라짐 | `... AND 1=1` vs `... AND 1=2` 응답 차이 |
| 시간 기반(Time-blind) | 응답 시간 | 본문 차이도 없을 때 | `SLEEP(3)`/`pg_sleep(3)` 삽입 시 응답 지연 |
| 인증 우회(Auth bypass) | 로그인 성공 여부 | 로그인 쿼리에 입력 결합 | `' OR 1=1--` 로 조건 무력화 |

> Juice Shop 로그인은 대표적으로 `' OR 1=1--` 계열 인증 우회가 성립하는 것으로 알려짐(수업 실습 대상).

### 2.2 사전 조건
- 입력이 서버측 쿼리에 도달하는 파라미터 식별(로그인, 검색, 정렬, id 조회 등)
- 원본(정상) 요청의 기준 응답 확보 — 상태코드, 본문 길이/해시, 응답 시간

### 2.3 탐지 신호 (원본 vs 변형 비교)
- **오류 기반**: 변형 요청에서 DB 오류 문자열(`SQL syntax`, `SQLITE_ERROR`, `unterminated`, `ORA-`, `PG::` 등) 등장
- **불리언 기반**: 참 조건과 거짓 조건 요청의 응답이 **유의미하게 다름**(길이/본문/결과 개수)
- **시간 기반**: 지연 페이로드에서만 응답 시간이 임계치 이상 증가(여러 번 재현되어야 신뢰)

### 2.4 신뢰도 스코어링 (개요)
- 단일 신호(우연 가능) < 재현되는 신호 < 여러 채널이 일치하는 신호
- 시간 기반은 네트워크 지터 영향 → 반복 측정 후 통계적으로 판단

### 2.5 성공 판정 근거
- 오류 기반: 주입 문자에 반응하는 DB 오류 메시지
- 불리언: 참/거짓 페이로드 응답 차이가 원본 대비 재현적으로 구분됨
- 시간: 지연 페이로드에서만 반복적으로 임계치 초과
- 인증 우회: 우회 페이로드로 인증 세션 획득
- 증거: 원본/변형 요청·응답, 상태코드/길이/시간 측정치 표

### 2.6 부하 제한
- 요청 변형 규칙 화이트리스트화, 재시도 상한 설정
- 시간 기반은 sleep 시간·반복 횟수 최소화 (테스트 사이트 부하 억제)

## 3. IDOR (Insecure Direct Object Reference)

객체 식별자(예: `id`, `orderId`)를 바꿔 요청했을 때, 권한 검사 없이 **다른 사용자의 객체**에 접근되는 취약점.

### 3.1 시나리오
- 사용자 A로 로그인 → A의 리소스 조회 요청에서 식별자 확인 (예: `/api/basket/1`, `/rest/user/2`)
- 식별자를 B(또는 인접 값)로 변경 → A의 권한으로 B의 리소스가 반환되는지 확인
- 수직(권한 상승: 일반→관리자) / 수평(같은 권한의 다른 사용자) 이동 모두 점검

### 3.2 사전 조건
- **최소 2개의 테스트 계정** (A, B) 및 각 계정 세션/토큰
- 각 계정이 소유한 객체 식별자 목록 확보
- 인증이 필요한 엔드포인트와 그 식별자 파라미터 위치 파악

### 3.3 탐지 신호
- A 세션으로 B의 식별자 요청 시 **200 + B의 데이터** 반환 (403/404가 아니라)
- 응답에 다른 사용자의 개인정보/객체 필드가 포함됨
- 식별자 증가/감소, UUID 추측, 예측 가능한 패턴에서 접근 성공

### 3.4 오탐 구분 기준
- 공개 리소스(원래 누구나 접근 가능)는 IDOR 아님 → 인증 없는 접근과 구분
- B의 식별자로 요청했는데 **A 자신의 데이터**가 오면 취약 아님(서버가 세션 기준으로 재해석)
- "접근 허용"의 근거는 반드시 **다른 계정 소유 객체의 식별 가능한 필드**로 확인

### 3.5 성공 판정 근거
- A의 인증 컨텍스트로 B 소유 객체 응답을 수신한 요청/응답 쌍
- 두 계정의 정상 응답과 교차 요청 응답을 나란히 비교한 증거표
- 접근 허용 시: 어떤 필드가 B의 것인지 명시

## 4. 탐지 → 검증 공통 데이터 형식 (초안)

세 Detector가 공유할 후보(candidate) 구조 (4주차에서 확정):

```json
{
  "vuln_type": "xss | sqli | idor",
  "location": {"url": "...", "method": "GET|POST", "param": "..."},
  "signal": "reflected | error-based | horizontal-idor ...",
  "evidence": {"request": "...", "response_excerpt": "...", "diff": "..."},
  "confidence": 0.0,
  "repro_steps": ["..."],
  "preconditions": {"accounts": [], "auth": "..."}
}
```
